# 5-Minute Walkthrough Video — Script & Checklist

The assessment requires a 5-minute screen recording (webcam optional) where
you **run the suite live** and narrate three specific things:

1. Where you handled a dynamic Lightning/shadow DOM component and why.
2. Why you chose your test data strategy (UI-based vs. API-based setup).
3. One thing that broke during development and how you debugged it.

Everything below is built around those three required points — don't skip
any of them, they're explicitly graded ("Process evidence" / "Stability" in
the evaluation rubric).

## Before you hit record

- [ ] Close the `.env` file / anything showing real credentials.
- [ ] Have these tabs/windows ready to flip to:
  1. Terminal, repo root.
  2. [SOLUTION.md](SOLUTION.md) (or [README.md](README.md)) for reference, not required on screen.
  3. [docs/shadow-dom-evidence.png](docs/shadow-dom-evidence.png) open in an image viewer or browser.
  4. VS Code with [src/pages/BasePage.ts](src/pages/BasePage.ts) and [tests/lead-conversion.spec.ts](tests/lead-conversion.spec.ts) open in tabs.
- [ ] Clear your terminal (`clear`) so the recording starts clean.
- [ ] Do one silent dry run beforehand so the live run doesn't hit a fresh-login/OTP prompt on camera (cached `storageState.json` should already be valid).
- [ ] Decide the exact command you'll run live — recommended:
  `npx playwright test --project=chromium` (finishes in ~2 minutes, leaves time to talk over it)

## Script (~5 minutes, timestamps are a guide not a hard rule)

### 0:00–0:20 — Intro

> "Hi, I'm [name]. This is my submission for the GovTech Salesforce QA
> automation assessment — a Playwright + TypeScript framework that covers
> Part A login, Part B Lead-to-Opportunity conversion with the API bonus,
> and Part C's shadow DOM and OTP-handling requirements. I'll run the suite
> live and walk through three things: a dynamic Lightning component I had
> to handle specially, my test data strategy, and one real bug I hit and
> how I debugged it."

### 0:20–0:45 — Kick off the live run

> "Let me start the suite running against my real Developer Edition org —
> I'll narrate while it executes."

Run:
```bash
npx playwright test --project=chromium
```

> "This first `setup` project revalidates my cached `storageState.json` —
> it never blindly trusts the cache, it actually opens a throwaway page and
> checks I'm still logged in before deciding whether to skip the real login.
> If that cache were missing or expired, it would perform a real login and
> handle Salesforce's email OTP challenge automatically — I'll come back to
> that in a moment."

*(Let it run in the background/split-screen for the next two talking
points, then come back to the terminal once it's done — the full run takes
roughly 2 minutes.)*

### 0:45–2:00 — Talking point 1: Shadow DOM / dynamic Lightning component

Switch to [docs/shadow-dom-evidence.png](docs/shadow-dom-evidence.png) and [src/pages/BasePage.ts](src/pages/BasePage.ts).

> "First required point: where I hit a dynamic Lightning component. The
> Lead Status field on the New Lead form renders as a `lightning-base-combobox`
> — here's the DevTools inspection I captured. Notice the button's `id` is
> `combobox-button-947` and it has a scoping class like `lwc-4kb6kaqheak` —
> both of those are regenerated by the Lightning Web Component runtime on
> every page load and every deploy. A naive locator like `#combobox-button-947`
> or a CSS class selector would pass today and silently break tomorrow.
>
> What doesn't change is the accessible contract the component renders:
> `role="combobox"` with `aria-label="Lead Status"`. So instead of CSS, my
> `BasePage.selectCombobox()` helper uses Playwright's `getByRole('combobox',
> { name: label })` — that targets the accessibility tree, which Playwright
> resolves through shadow roots automatically, so it stays stable regardless
> of how the internal DOM re-renders. I use the same accessible-role
> approach for every Lightning combobox and lookup field in this framework,
> including the Account/Contact search in the Convert Lead dialog."

### 2:00–3:15 — Talking point 2: test data strategy

Switch to [src/data/testDataFactory.ts](src/data/testDataFactory.ts).

> "Second required point: my test data strategy, and why UI-based rather
> than API-based setup. Every Lead in this suite is created by actually
> driving the real 'New Lead' form through the UI — first name, last name,
> company, email, lead source, all of it — rather than pre-seeding records
> through the Salesforce REST or Bulk API and only using the UI for
> assertions.
>
> I chose UI-based setup for two reasons. First, Lead creation itself is
> literally the feature under test in Part B — if I seeded it via API, I'd
> never actually exercise the form validation and save flow the assessment
> asks me to automate. Second, it keeps the framework dependency-light: no
> separate API client, auth flow, or session-management code path to
> maintain alongside the UI automation.
>
> For uniqueness under parallel execution, I didn't use a library like
> Faker — it's ESM-only and broke this CommonJS project outright, which I
> ended up documenting as the 'one thing that broke' story, coming up next.
> Instead `createLeadData()` here generates names and companies from small
> local word lists plus a `crypto.randomBytes` suffix, so two parallel
> workers can never collide on the same Lead identity — zero dependencies,
> zero ESM/CJS conflicts.
>
> The one place I do validate the real backend API directly is the Part B
> bonus: after conversion, I capture the actual Lightning/Aura network
> response for the Convert Lead action and assert on real fields from it —
> that's covered in NOTES.md."

### 3:15–4:30 — Talking point 3: one thing that broke, and how you debugged it

> "Third required point: one real thing that broke. The most interesting
> one was in my Lead-to-Opportunity conversion test for the 'existing
> Account already matches' path. I reused a fixed Company name across test
> runs so the Convert Lead dialog's Account search would find a real
> existing match — Salesforce's search index needs real wall-clock time to
> catch up on a freshly created record, so I couldn't create and
> immediately search for the same Account in one run.
>
> After a few runs, though, the 'New Lead' save started failing — it looked
> like a plain UI timing flake at first: the Save button click wasn't
> completing. I spent a couple of attempts trying different click-retry and
> wait strategies before I actually looked at a screenshot of what was on
> screen at the failure point. The New Lead modal was still open, with a
> 'Similar Records Exist' dialog on top of it — Salesforce's Lead-level
> duplicate rule had quietly started blocking the save, because I was
> reusing the *exact same* full identity — company, first name, last name,
> and email — every run, and after enough runs that Lead became an exact
> duplicate of one from a prior run.
>
> The fix wasn't a UI timing fix at all — no amount of re-clicking Save got
> past that dialog, because it's a hard block, not a soft warning. The real
> fix was redesigning the test data itself: only fix the Company name across
> runs — the field the Account match actually depends on — and randomize
> everything else per run, so the Lead is never an exact duplicate of a
> prior one. That's the kind of bug you only catch by stepping back and
> questioning whether your retry logic is solving the right problem at all,
> rather than adding another retry on top of the wrong assumption."

### 4:30–5:00 — Wrap-up

Switch back to the terminal, show the green summary.

> "And here's the suite passing — both the Lead creation and conversion
> scenarios, the negative-path tests, and the API-bonus assertions on the
> real conversion response. This also runs cross-browser on Chromium and
> WebKit, and in CI via GitHub Actions on every push. Full details on setup,
> the API payload I captured, and the shadow DOM evidence are in README.md,
> SOLUTION.md, and NOTES.md. Thanks for watching."

## If you're short on time, cut here first

The script above runs a little over 5 minutes if read in full. If you need
to trim, cut in this order (least to most important, since all three bullet
points are explicitly graded — don't cut any of them entirely):

1. Shorten the wrap-up to one sentence.
2. Trim the test-data-strategy section's Faker detour to one sentence
   ("I avoided Faker because of an ESM conflict — see NOTES.md").
3. Shorten talking point 3 to the root cause and fix only, skip the
   narrative of the wrong attempts.

Do **not** cut the live test run itself, or any of the three required
talking points — those are the actual deliverable.
